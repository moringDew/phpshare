# ADR-001：业务数据库采用 MySQL 8.0

## 状态

已决定，2026-11-10。

## 决策

平台业务数据库采用 **MySQL 8.0 + InnoDB**。历史行情和大规模因子数据继续采用 **Parquet + DuckDB**，Redis 仅承担缓存与任务队列，不作为最终账本。

## 原因

团队已经熟悉 MySQL，能够降低建模、SQL 开发、问题定位、备份恢复和日常运维成本。平台第一阶段面向日线回测与模拟交易，MySQL 8.0 的事务、行级锁、外键、窗口函数、JSON、CTE 和分区能力可以满足业务要求。

PostgreSQL 在复杂约束、JSONB 和部分分析能力上更灵活，但这些优势不足以抵消团队切换数据库带来的学习与运维成本。复杂行情分析由 DuckDB 承担，因此不会把大规模时序分析压力集中到 MySQL。

## 实施约束

- 所有核心业务表使用 InnoDB、`utf8mb4` 和明确的排序规则。
- 金额、价格、费用和数量使用 `DECIMAL`，禁止使用 `FLOAT/DOUBLE` 记账。
- 订单采用客户端订单号唯一索引实现幂等。
- 资金、成交、订单和持仓更新必须处于同一事务，或采用可审计的事件与补偿机制。
- 固定锁定顺序，降低并发更新账户和持仓时的死锁概率。
- 关键业务约束同时在数据库和服务层校验，不依赖前端。
- 使用 Flyway 或 Alembic 管理表结构版本，禁止手工修改生产库结构。
- 开启慢查询日志，设置连接池、备份、恢复演练和监控。
- Redis 任务消息不能替代数据库中的任务、订单和资金最终状态。

## 重新评估条件

当出现 MySQL 无法合理解决的复杂分析、扩展类型或约束需求，且迁移收益高于团队成本时，再评估 PostgreSQL。当前没有迁移需要。
